# רשימת תנאים לעלייה לאוויר

**כלל:** האתר לא מפורסם עד שכל הסעיפים ברשימה מתקיימים בייצור. עמודת "ייצור" חייבת להיות "בוצע" בכל שורה, גם כשעמודת "מקומי" מראה בדיקה אוטומטית שעוברת.

הרשימה מאחדת את התנאים מסיפורים 4.1 (הקשחה), 4.2 (ניטור מיילים), 4.3 (גיבוי ושחזור) ו-4.4 (בדיקות נעילה). הסדר הוא הסדר המומלץ: קודם מה שלוקח זמן ותלוי בגורמים חיצוניים, אחר כך תצורה, ובסוף אימות ועלייה.

- **אחראים:** מנהלת הקורס, בונת האתר, הארגון.
- **מקומי:** "אומת אוטומטית" (עם קישור לבדיקה או לסקריפט), "לא רלוונטי" (אין מה לבדוק מקומית) או "דורש פעולה".
- **ייצור:** "דורש פעולה" או "בוצע (תאריך, מי)". סעיף שמקומית אומת אוטומטית עדיין דורש הוכחה בייצור.

מה שננעל בבדיקות אוטומטיות מקומיות (ריצה על Postgres אמיתי):

- כל נקודות הקצה סגורות כברירת מחדל, והאנונימיות הן רשימה מפורשת: `server/Tests/EndpointSecurityTests.cs`.
- אין מייל, נייד או אסימון בתגובות של נקודות ה-GET וה-POST הציבוריות ושל שגיאותיהן: `server/Tests/PublicPrivacyTests.cs`.
- שני אדמינים נוצרים ללא כפילות, וכל אחד חייב להחליף סיסמה ולהירשם ל-TOTP לפני גישה לניהול: `server/Tests/AdminBootstrapTests.cs` (עם `AdminAuthTests` מסיפור 1.3 ו-`AdminTotpTests` מסיפור 1.4).

שאילתות להוכחת סעיפים 9 ו-10:

```sql
SELECT has_table_privilege('app', 'audit_log', 'UPDATE')   AS app_update_audit,   -- false
       has_table_privilege('app', 'audit_log', 'DELETE')   AS app_delete_audit,   -- false
       has_table_privilege('app', 'audit_log', 'TRUNCATE') AS app_truncate_audit, -- false
       has_schema_privilege('app', 'public', 'CREATE')     AS app_create_schema,  -- false
       has_table_privilege('app', 'audit_log', 'INSERT')   AS app_insert_audit;   -- true
SELECT count(*) AS objects_owned_by_app FROM pg_class c JOIN pg_roles r ON r.oid = c.relowner WHERE r.rolname = 'app'; -- 0
```

שחזור מהרשאה שגויה: מריצים שוב `server/db/roles.sql` ומריצים מחדש את השאילתות.
