# גיבוי ושחזור (סיפור 4.3)

מסמך תפעול לגיבוי ולשחזור של בסיס הנתונים. בריצה המקומית הגיבוי הוא `pg_dump` בפורמט custom (`-Fc`) מתוך הקונטיינר `resume-dev-pg`, והשחזור הוא `pg_restore` למסד נפרד. בייצור (Render) הגיבוי והשחזור לנקודת זמן מסופקים על ידי Render, ראו `docs/launch-checklist.md`.

## מי מבצעת

- מנהלת הקורס: מחליטה על תדירות הגיבוי, מדיניות השמירה והמחיקה, ומי רשאית לגשת לקבצי הגיבוי.
- בונת האתר: מריצה את הסקריפט ואת תרגיל השחזור, ומתעדת את התוצאה.

## פקודות

הקונטיינר `resume-dev-pg` חייב לרוץ. מתיקיית הפרויקט:

```powershell
# גיבוי: קובץ backups/resume-<תאריך>-<שעה>.dump (התיקייה ב-.gitignore)
powershell -File scripts/backup-restore.ps1 backup

# שחזור למסד חדש resume_restore_check (נמחק ונוצר מחדש בכל ריצה)
powershell -File scripts/backup-restore.ps1 restore backups/resume-20261023-120000.dump

# אימות: גיבוי, שחזור למסד resume_restore_check, השוואת ספירות (פרופילים, גרסאות, נתונים פרטיים, מחזורים, יומן ביקורת) מול המקור, ומחיקה תמיד של מסד היעד
powershell -File scripts/backup-restore.ps1 verify
```

פרמטרים (כולם עם ברירות מחדל): `-Container resume-dev-pg`, `-SourceDatabase resume`, `-TargetDatabase resume_restore_check`, `-User postgres`, `-Password` (ברירת מחדל: `$env:PGPASSWORD`, ואם אינו מוגדר `dev`), `-BackupDir backups`, ו-`-Force`. הסקריפט אינו מדפיס את הסיסמה, ומחזיר קוד יציאה שאינו אפס בכל כשל.

### הגנות

`restore` מסרב כאשר:

- מסד היעד זהה למסד המקור, או הוא אחד מ-`resume`, `postgres`, `template0`, `template1`, `resume_e2e`, או ששמו אינו תקין, או שקובץ הגיבוי חסר או פגום. אלה סירובים מוחלטים: `-Force` אינו עוקף את הראשונים (זהה למקור ומסד מוגן);
- שם מסד היעד אינו מתחיל ב-`resume_restore`; רק `-Force` מאפשר זאת;
- למסד היעד יש חיבורים פעילים (נבדק ב-`pg_stat_activity`); רק `-Force` מנתק אותם ומוחק את המסד. בלי `-Force` המחיקה היא `DROP DATABASE` רגיל שנכשל אם נוצר חיבור מאוחר.

כלומר `-Force` עוקף רק שני סירובים: חיבורים פעילים ויעד שאינו `resume_restore*`. מסד יעד שנוצר ושחזורו נכשל נמחק מיד, כי הוא עלול להכיל נתונים אישיים.

ההגנות שנבדקות לפני כל קריאה ל-docker מכוסות בבדיקות אוטומטיות (`BackupRestoreScriptGuardTests`, מריצות את הסקריפט עצמו ב-Windows). הגנת החיבורים הפעילים נבדקה ידנית פעם אחת (חיבור פתוח ל-`resume_restore_check`, `restore` בלי `-Force` סירב עם קוד 1).

כדי לבדוק שהאפליקציה עולה מול המסד המשוחזר מפעילים אותה עם `DATABASE_URL` שמצביע על `resume_restore_check` (המיגרציות לא אמורות לשנות דבר).

## בדיקה אוטומטית

`server/Tests/BackupRestoreTests.cs` רצה על Postgres אמיתי (Testcontainers) ואינה נוגעת במסד הפיתוח: זורעת מחזור, פרופיל מאושר עם תמונה, גרסה ממתינה, נתונים פרטיים, בקשת פרטי קשר ושורת `AuditLog`; מריצה את אותם `pg_dump -Fc` ו-`pg_restore --no-owner --exit-on-error`; מרימה את השרת מול המסד המשוחזר; ומוכיחה שהיסטוריית המיגרציות זהה, `GET /profiles` ו-`GET /profiles/{id}` זהים, התמונה זהה בייטים, וכל השורות קיימות בלי כפילויות.

```powershell
dotnet test server --filter "FullyQualifiedName~BackupRestore"
```

## RPO ו-RTO

| | בפיתוח (מקומי) | ביעד ייצור (Render) |
|---|---|---|
| RPO (כמה נתונים מותר לאבד) | עד תדירות הגיבוי שתיבחר (למשל גיבוי יומי = עד יום) | דקות, ובלבד ששחזור לנקודת זמן מופעל (תנאי עלייה) |
| RTO (זמן חזרה לפעולה) | דקות: `restore` ועלייה של השרת | נמדד בתרגיל השחזור בייצור ומתועד ב-`docs/launch-checklist.md` |

תדירות הגיבוי המקומית טרם נקבעה; ההחלטה בידי מנהלת הקורס.

## אזהרות

- אין לשחזר על מסד חי. השחזור תמיד נעשה למסד נפרד, ורק אחרי בדיקה מחליפים את החיבור של האפליקציה.
- הגיבוי כולל נתונים אישיים (מייל, נייד, בקשות פרטי קשר, תמונות). שומרים אותו מוצפן ובגישה מצומצמת, ולא מעבירים אותו במייל או בצ'אט.
- מחיקת גיבויים ישנים נעשית לפי מדיניות שמירה שטרם נקבעה (תנאי עלייה). עד אז מוחקים ידנית גיבויים שאינם נחוצים.
- אחרי שחזור למסד חדש בייצור מריצים שוב את `server/db/roles.sql` (ראו README, "תפקידי בסיס הנתונים") כי הגיבוי נלקח ללא בעלים (`--no-owner`).
